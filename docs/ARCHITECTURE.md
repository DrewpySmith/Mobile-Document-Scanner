# ScanMind — Architecture Overview

## 1. Database — `lib/core/database/`

ScanMind uses Isar to store scans locally on the device. The app opens a single Isar database in the app's documents directory on first use and guards against opening it twice — which matters during development hot restart.

Each saved scan is a `ScanDocument` row. It holds the title, creation date, PDF file path, the original page image paths, the OCR text, and an optional cached translation. It also exposes a computed `searchText` field that combines the title, OCR text, and translation into a single string, which Isar indexes for fast case-insensitive search across all documents.

The Isar schema is generated by `build_runner` from the `@collection` and `@Index` annotations, so the `.g.dart` file should never be edited by hand.

`IsarService` is a thin wrapper around the common operations: open the database, list all documents, save one, delete one, and clear everything. All writes run inside a transaction. The service exposes the database as a `Future<Isar>`, so every consumer awaits the handle — works fine, though a Riverpod `FutureProvider` would be more idiomatic.

## 2. Network — `lib/core/network/dio_client.dart`

Network calls go through Dio. The only external service the app talks to is MyMemory, a free public translation API. The client has the base URL, timeouts, and a JSON `Accept` header configured up front, and exposes a single `translateText` method that hits the `/get` endpoint with the source text and a `source|target` language pair.

Error handling is inline: connection timeouts get a friendly message, HTTP 429 (rate limit) gets its own message, and other failures bubble up the original error. There is no logging, no retry logic, and the Dio client is instantiated inside the class with no way to inject a mock for testing. The base URL is also hardcoded, which would be a problem if the app ever needed to point at a different environment.

## 3. Services — `lib/services/`

Two services do the heavy native work.

`OcrService` wraps Google ML Kit's on-device text recognizer. It can process a single image or a list of images, and for multi-page scans it reuses the same recognizer across all pages — this avoids reinitializing the native engine per page, which is the expensive part. The service always closes the recognizer in a `finally` block to free native memory. When no text is found, it returns a placeholder string telling the user the page was empty, which mixes a UX concern into what should be a pure data layer.

`PdfService` builds a real PDF from a list of scanned images using the `pdf` package. Each image becomes one A4 page with consistent margins and `BoxFit.contain` so nothing is cropped. The output file is saved into the app's documents directory with a sanitized filename and a millisecond timestamp. The service returns the saved path and also has a `deletePdf` helper, but it does not delete the related database row — that coordination lives elsewhere (or is currently missing).

## 4. How the Layers Connect

Features call services. Services call core. Core has no opinion about features.

```
features/  →  services/  →  core/{database, network}/
   UI         pure Dart       Isar, Dio
```

Right now features talk to `IsarService`, `OcrService`, `PdfService`, and `DioClient` directly. That is fine at the current scale, but a repository layer would help once there are more features or composed workflows.

## 5. What's Missing

The biggest gaps are logging, a typed error model (everything is a string `Exception`), unit tests for the services, and proper dependency injection so the database and HTTP client can be mocked. None of these are blockers for v1, but they will all become painful as the app grows.
